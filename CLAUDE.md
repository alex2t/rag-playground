# RAG Playground

A presentation project. It is a controlled study of which RAG techniques improve retrieval and answer quality: starting from a documented default baseline, it changes one variable at a time on two stacks, and it deploys the system with a CI evaluation gate. FastAPI + React, Docker on a Hostinger VPS (staging and prod). The roadmap is in `plan.md`, decisions are in `decision.md`, and bugs and reviews are in `fix.md`.

## Working with the user
- **When asking the user a question, present every fact needed to decide**, in plain words: what the problem is, why it happens, what each option changes, its cost and its trade-off. Define every term and id used (such as `multi_doc` or `T30`); never assume the user remembers them.
  - Before asking, check each question: could someone who has not read `plan.md` or `decision.md` answer it? If not, rewrite it.
  - Explain every technical word in one sentence (gate, judge, bootstrap, confidence interval, run, ...). Explain what the thing is *for* before asking how to set it.
  - Say what happens next: when the decision matters, what it costs (in dollars), and what happens if the user does not decide now.
  - One topic per question; give a recommendation; prefer a yes/no question where possible.
- **Do not use the user's OpenRouter credential in this project** once the Step 2 dataset is finished (the last authorized use is completing `tests.jsonl`). Claude develops; Antigravity verifies. Do not run any script, test or job that calls OpenRouter (including `-m live` tests and dataset stages); write the code and hand runs to the user. When a later step needs LLM calls (evaluation runs, the CI gate), raise how they will be paid for with the user first.
- **Always follow best practice. The RAG analysis must have real value:** results must survive scrutiny by an evaluation expert. When a problem is found, fix its root cause. Never relax a check, a rule or the data to make results look better or a step easier.
- **Dataset quality comes first:** every fact in the KB must be consistent, and every gold answer must be unambiguous. A contradiction in the data invalidates the scores built on it.
- Simple, incremental steps. Validate each one before moving on.
- Best practice by default. Where a shortcut is taken, record it in `decision.md` as "Not best practice", with the production alternative.
- Be honest about the sources of formulas and thresholds. Never present a custom choice as a standard.

## Stack
- Backend: Python 3.12 with `uv`. Run with `uv run ...` and add dependencies with `uv add ...`. Never use pip or a bare `python`.
- Frontend: Vite + React + TypeScript + Tailwind + Recharts. Built in a multi-stage Dockerfile and served by FastAPI from the same release image.
- Stack A: OpenAI Vector Store (`OPENAI_API_KEY`). Stack B: fastembed `nomic-ai/nomic-embed-text-v1.5` + Qdrant, with no torch. Always use the `search_document:` and `search_query:` prefixes.
- Both stacks index the same chunk set, produced by LlamaIndex's `SentenceSplitter` (unmodified, T39) and saved to `var/chunk_sets/`. Stack A uploads one file per chunk, so OpenAI does not split it again.
- Every answer, judge, rerank and enrichment LLM call goes through OpenRouter (`OPENROUTER_API_KEY`, `base_url=https://openrouter.ai/api/v1`). Temperature is 0 everywhere, and is sent only if the model's `supported_parameters` includes it.
- The model catalogue, judge, chunk sizes, ladder and gates live only in `backend/src/rag_playground/settings.py`. Check model IDs against `https://openrouter.ai/api/v1/models` before changing them.
- Chunk sizes are in tokens. Tests have gold `source_docs` and a `split` (`dev` = 192, `heldout` = 48). Never tune on held-out questions.
- SQLite per environment. Long jobs run in the background and the UI polls `/api/jobs/{id}`. Spend is capped by `BUDGET_USD`.
- Every run stores reproducibility metadata: git SHA, model `canonical_slug`s, prompt hash, dataset hash, chunk-set id and ranking options.
- A shared edge Caddy handles TLS and basic auth for `staging.<domain>` and `<domain>`. Qdrant is never exposed publicly.
- Secrets live in a `.env` file per environment on the VPS (owner-only, never committed) and in GitHub Actions secrets for CI.

## Verification by Antigravity
At the end of every piece of code Claude writes or changes, give the user a ready-to-paste prompt for Antigravity (Gemini) to verify it. `agent.md` holds Antigravity's standing instructions: read it, never change it. The prompt states: the commit or files to review, the context and plan step, what to check, issues Claude already knows about, and safety limits (no paid API calls, no `-m live`, memory: fastembed batch size 4 or less on this 8 GB PC). It asks for the `agent.md` review format.

**Verify every Antigravity finding, action and suggestion before acting on it.** Antigravity can be wrong. Check each claim against the code, the data or a run, and tell the user the result: confirmed (with the evidence), partly right (what holds and what does not), or wrong (why). Apply only what is confirmed; if a suggested fix is not the root-cause fix, say so and propose the better one. Never apply a suggestion just because the reviewer made it.

`gemReview.md` is Antigravity's backlog of open actions only (`agent.md` rules). Antigravity removes items once they are done and verified, and empties the file when all are done. An empty `gemReview.md` means nothing is open, not lost work. The lasting record of findings and fixes is `fix.md`.
